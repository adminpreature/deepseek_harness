# MVP 核心功能范围（修订版 v2）

## 产品定位

**核心定位：** 企业员工协作管理平台 + AI 全员助手

**市场差异化：**
- **vs WorkBuddy/豆包：** 他们只有 AI 能力，我们有完整的企业组织管理
- **vs 钉钉/飞书/企业微信：** 他们只有协作管理，AI 能力弱，我们深度融合
- **独特价值：** AI 能力 + 企业管理系统深度集成，让 AI 真正融入组织架构和工作流程

**一句话描述：**
> 一个自带完整企业管理系统的 AI 工作平台，为每位员工提供智能工作助手，串联企业工作流程

---

## 核心卖点（按重要性排序）

### 🏆 第一核心：完整的企业协作管理系统
- 组织架构管理（公司 → 部门 → 团队）
- 任务协作和流转（上下级派发、跨部门协同）
- 基于角色的权限体系
- 多租户 SaaS 架构

### 🤖 第二核心：全员 AI 工作助手
- 每个员工都有 AI 助手（角色感知、权限感知）
- AI 融入工作流程（任务扩写、知识问答、文档生成）
- 对标 WorkBuddy/豆包 的 AI 能力

### 🔗 第三核心：工作流程串联
- 任务关联和依赖
- 跨部门协作（手动触发，Phase 2 自动化）
- 企业知识沉淀和复用

## 一、功能优先级排序

### P0 级别（企业协作基础设施 - 核心中的核心）

#### 1. 多租户系统
**优先级：** P0  
**原因：** SaaS 架构的基础，支持多个企业独立使用

**核心能力：**
- 租户注册和配置管理
- 数据完全隔离（基于 tenant_id）
- 租户上下文自动注入
- 租户级别的定制化（logo、主题色、功能开关）

**验收标准：**
- [ ] 可以创建多个租户，数据 100% 隔离
- [ ] 每个 API 请求自动携带租户上下文
- [ ] 租户 A 无法访问租户 B 的任何数据
- [ ] 支持租户配置（公司名称、logo、主题色）

**不包括（留待后续）：**
- 复杂的资源配额和限流
- 细粒度的功能开关
- 租户间数据共享

---

#### 2. 组织架构管理
**优先级：** P0  
**原因：** 企业协作的核心，定义"谁属于哪个部门、谁管理谁"

**核心能力：**
- 公司/部门/团队的层级结构（树形）
- 员工归属关系（一个员工可以属于多个部门）
- 上下级汇报关系（部门负责人）
- 组织架构可视化（组织树）

**验收标准：**
- [ ] Admin 可以创建部门层级（如：公司 → 销售部 → 华东区 → 上海组）
- [ ] 可以指定部门负责人
- [ ] 员工可以查看自己所属的部门和上级
- [ ] 支持员工跨部门（如：既属于销售部，也属于某个项目组）

**示例组织结构：**
```
某科技公司
├── 销售部
│   ├── 华东区（负责人：张经理）
│   │   ├── 上海组
│   │   └── 杭州组
│   └── 华南区
├── 研发部（负责人：李经理）
│   ├── 前端组
│   ├── 后端组
│   └── 测试组
└── 财务部
```

**不包括（留待后续）：**
- 复杂的矩阵式组织结构
- 虚拟团队（跨部门项目组）
- 组织变更历史记录

---

#### 3. 用户认证和权限
**优先级：** P0  
**原因：** 安全和访问控制的基础

**核心能力：**
- 用户注册、登录（密码认证）
- JWT token 生成和验证
- 基于角色的权限控制（RBAC）
- 三个核心角色：
  - **Admin（管理员）**：管理整个租户（组织架构、用户、全局配置）
  - **Manager（经理）**：管理所属部门（成员、任务、部门数据）
  - **Member（员工）**：使用系统（自己的任务、AI 助手、知识库）

**验收标准：**
- [ ] 用户可以注册和登录
- [ ] Admin 可以：
  - 创建和管理组织架构
  - 添加/删除/编辑用户
  - 查看所有任务和数据
- [ ] Manager 可以：
  - 管理自己部门的成员
  - 给下属派发任务
  - 查看部门内的所有任务
- [ ] Member 可以：
  - 查看和完成自己的任务
  - 使用 AI 助手
  - 查询知识库

**权限矩阵示例：**

| 资源 | Admin | Manager | Member |
|-----|-------|---------|--------|
| 组织架构 | 增删改查 | 只读 | 只读（自己部门）|
| 用户管理 | 增删改查 | 本部门增删改查 | 只读（自己）|
| 任务管理 | 全部 | 本部门全部 | 自己的任务 |
| 知识库 | 全部 | 本部门 | 有权限的文档 |

**不包括（留待后续）：**
- OAuth 第三方登录（飞书、企业微信）
- 细粒度的资源级权限
- 多因素认证

---

#### 4. 任务管理和协作
**优先级：** P0  
**原因：** 企业协作的核心场景，工作流程的载体

**核心能力：**

**4.1 任务基础功能**
- 任务 CRUD（创建、查看、编辑、删除）
- 任务分配（单人/多人负责）
- 任务状态流转（todo → in_progress → review → done）
- 任务优先级（低、中、高、紧急）
- 任务截止日期和提醒
- 任务标签和分类

**4.2 协作场景（核心）**

**场景 A：上下级任务派发**
```
1. 领导（Manager）创建任务
2. 分配给下属（Member）
3. 下属接受任务并开始执行
4. 下属标记为"待审核"
5. 领导审核并标记为"已完成"
```

**场景 B：跨部门协作**
```
1. 销售部创建任务"客户 A 签约项目"
2. 手动创建关联任务：
   - 研发部："开发客户 A 的定制功能"
   - 财务部："为客户 A 开具发票"
3. 各部门可以看到关联任务
4. 任务完成顺序有依赖关系（销售完成 → 研发开始）
```

**场景 C：子任务拆解**
```
1. 经理创建主任务："完成 Q1 销售目标"
2. 拆解为子任务：
   - 子任务 1：开发 10 个新客户（分配给张三）
   - 子任务 2：维护 20 个老客户（分配给李四）
   - 子任务 3：完成 50 万业绩（分配给王五）
3. 所有子任务完成后，主任务自动标记为完成
```

**4.3 任务视图**
- 看板视图（Kanban）：按状态分列（待办、进行中、已完成）
- 列表视图（List）：按部门、负责人、优先级筛选
- 日历视图（Calendar）：按截止日期展示

**4.4 任务通知**
- 任务被分配时通知负责人
- 任务状态变更时通知创建者
- 任务即将到期时提醒负责人

**验收标准：**
- [ ] Manager 可以创建任务并分配给本部门或其他部门的成员
- [ ] 支持任务依赖关系（任务 B 必须等任务 A 完成后才能开始）
- [ ] 支持子任务（主任务下有多个子任务）
- [ ] 任务看板视图（按状态分列：待办、进行中、已完成）
- [ ] 任务列表视图（按部门、负责人、优先级筛选）
- [ ] 任务关联（销售任务关联研发任务、财务任务）
- [ ] 任务到期提醒（截止日期前 1 天提醒）
- [ ] 任务状态变更通知（分配、完成、审核）

**关键指标：**
- 领导可以看到所有下属的任务进度
- 员工可以看到自己的待办任务（按优先级和截止日期排序）
- 跨部门任务可以明确看到关联关系和依赖

**不包括（留待后续）：**
- 甘特图
- 燃尽图
- 工时统计报表
- 自动化工作流（触发器 + 动作）

### P1 级别（AI 增强能力 - 差异化竞争力）

#### 5. 全员 AI 工作助手
**优先级：** P1  
**原因：** 对标 WorkBuddy/豆包，让 AI 融入每个员工的工作流程

**核心能力：**

**5.1 AI 对话助手**
- 每个员工都有独立的 AI 对话窗口
- AI 能感知用户角色和权限（销售员工 vs 研发员工）
- AI 能访问用户有权限的企业数据
- 支持多轮对话和上下文理解

**5.2 AI 增强的任务管理**
- **任务智能扩写**：领导输入简短描述 + 关键词，AI 自动生成详细任务描述、子任务拆解、推荐负责人
- **任务建议**：AI 根据历史数据建议任务优先级、预估工时
- **进度提醒**：AI 主动提醒即将到期的任务

**5.3 AI 文档生成**
- 根据对话生成 Word 文档（会议纪要、客户邮件、报告）
- 根据数据生成 Excel 报表
- 根据要点生成 PPT 演示文稿
- 自动应用企业 branding（logo、颜色、模板）

**5.4 AI 知识问答**
- 基于企业知识库的智能问答
- 权限感知（不同用户看到不同文档）
- 引用来源标注（回答来自哪份文档）
- 跨文档综合回答

**验收标准：**
- [ ] 每个员工登录后可以与 AI 对话
- [ ] AI 能理解用户角色（销售员工问销售问题，研发员工问技术问题）
- [ ] 任务扩写功能：
  - 输入：标题 + 关键词
  - 输出：详细描述 + 子任务列表 + 推荐负责人
  - 生成时间 < 5 秒
- [ ] 文档生成：
  - 对话式生成 Word/Excel/PPT
  - 自动应用企业模板
  - 生成的文档可下载并关联到任务
- [ ] 知识问答：
  - 用户提问 → AI 检索知识库 → 返回答案 + 引用来源
  - 响应时间 < 3 秒
  - 准确率 > 75%（基于测试问题集）

**对标参考：**
- **WorkBuddy**：100+ AI 专家、端到端任务交付
- **豆包工作**：多 Agents 并行、与飞书深度集成
- **我们的差异化**：AI + 完整的企业组织管理系统

**不包括（留待后续）：**
- 预设的专业 AI 助手（销售助手、研发助手、财务助手）
- AI 主动工作（自动发现问题并处理）
- 多模态输入（语音、图片）

---

#### 6. 企业知识库
**优先级：** P1  
**原因：** 企业知识沉淀，AI 问答的数据基础

**核心能力：**
- 上传企业文档（PDF、Word、Markdown、TXT）
- 文档自动解析、分块、向量化
- 向量数据库存储（Milvus/Pinecone）
- 语义检索（RAG）
- 权限控制（部门级、用户级）

**验收标准：**
- [ ] Admin 可以上传文档到知识库
- [ ] 支持按部门组织文档（销售部文档、研发部文档）
- [ ] 文档自动向量化存储
- [ ] 支持全文搜索和语义搜索
- [ ] 权限控制：
  - 公开文档：所有人可见
  - 部门文档：只有部门成员可见
  - 私有文档：只有上传者可见
- [ ] AI 问答时自动检索相关文档

**不包括（留待后续）：**
- 文档多人协同编辑
- 文档版本控制
- 文档评论和讨论
- 多模态文档（图片、视频、音频）

### P2 级别（用户体验增强）

#### 7. 基础 Web UI
**优先级：** P2  
**原因：** 用户交互的必需界面

**核心页面：**

**7.1 登录和注册**
- 登录页面（用户名/密码）
- 忘记密码
- 首次登录引导

**7.2 工作台 Dashboard**
- 个人待办任务（按优先级和截止日期排序）
- 最近活动（任务分配、状态变更）
- 快速入口（创建任务、AI 助手、知识库）
- 通知中心

**7.3 任务管理**
- 任务看板视图（拖拽卡片切换状态）
- 任务列表视图（按部门、负责人、优先级筛选）
- 任务详情页（描述、子任务、附件、操作历史）
- 创建任务对话框（支持 AI 扩写）

**7.4 AI 对话窗口**
- 固定在右下角的 AI 助手按钮
- 弹出式对话窗口（类似客服聊天）
- 支持文本输入和快捷命令
- 实时流式输出（打字机效果）

**7.5 知识库**
- 文档列表（按部门、标签筛选）
- 文档详情页（在线预览 PDF/Word/Markdown）
- 文档上传（拖拽上传）
- 搜索功能（全文搜索 + 语义搜索）

**7.6 组织架构**
- 组织树视图（公司 → 部门 → 团队）
- 人员列表（姓名、部门、角色、联系方式）
- 部门详情（负责人、成员、统计数据）

**7.7 管理后台（仅 Admin 可见）**
- 用户管理（添加、编辑、删除、重置密码）
- 组织架构管理（创建/编辑部门）
- 租户配置（公司信息、logo、主题色）
- 系统设置（AI 模型选择、知识库配置）

**验收标准：**
- [ ] 用户可以通过 Web 界面登录
- [ ] Dashboard 展示个人待办任务和通知
- [ ] 可以在看板视图中拖拽任务卡片
- [ ] 可以创建任务并触发 AI 扩写
- [ ] 可以与 AI 对话（知识问答、文档生成）
- [ ] 可以浏览和搜索知识库文档
- [ ] Admin 可以管理用户和组织架构

**UI 设计原则：**
- 简洁实用，不追求精美（MVP 阶段）
- 响应式布局（PC 端优先）
- 使用成熟的组件库（Ant Design / shadcn/ui）

**不包括（留待后续）：**
- 移动端 App
- 深色模式
- 国际化（i18n）
- 复杂的数据可视化图表
- 实时协作（多人同时编辑）

## 二、MVP Demo 演示场景

### 场景：「销售团队使用 AI 助手管理客户跟进工作」

**参与角色：**
- **销售总监（Admin）**：张总
- **销售经理（Manager）**：李经理（华东区负责人）
- **销售员工（Member）**：王销售

**演示流程：**

---

### Step 1: 销售总监配置系统（5 分钟）

**1.1 登录管理后台**
```
- 访问系统 URL
- 使用 Admin 账号登录
- 进入管理后台
```

**1.2 设置组织架构**
```
某科技公司
├── 销售部
│   ├── 华东区（负责人：李经理）
│   │   ├── 王销售
│   │   └── 赵销售
│   └── 华南区
└── 研发部
```

**1.3 上传企业知识库**
```
- 上传《销售手册》（PDF）
- 上传《客户谈判技巧》（Word）
- 上传《产品介绍》（PPT）
- 设置权限：销售部可见
```

---

### Step 2: 销售经理派发任务（3 分钟）

**2.1 登录系统**
```
- 李经理使用账号登录
- 进入工作台 Dashboard
```

**2.2 创建任务（使用 AI 扩写）**
```
点击「新建任务」

输入：
  标题：跟进客户 A 的采购需求
  关键词：价格谈判、合同审核、预算 50 万
  负责人：王销售
  截止日期：2026-10-15

点击「AI 智能扩写」

AI 生成：
  详细描述：
    客户 A 是一家中型制造企业，计划采购我司的 SaaS 产品...
    [完整描述]
  
  子任务：
    1. [ ] 调研客户背景和需求（预估 2h）
    2. [ ] 准备报价方案（预估 3h）
    3. [ ] 发送跟进邮件（预估 1h）
    4. [ ] 合同审核和签订（预估 4h）
  
  推荐：根据历史数据，王销售处理过类似任务，建议优先分配

经理审核后点击「确认创建」
```

**2.3 任务分配**
```
- 系统自动通知王销售
- 王销售的 Dashboard 显示新任务
```

---

### Step 3: 销售员工执行任务（10 分钟）

**3.1 查看任务**
```
- 王销售登录系统
- Dashboard 显示「跟进客户 A 的采购需求」任务
- 点击任务查看详情
- 查看 AI 生成的子任务列表
```

**3.2 向 AI 助手提问（知识库问答）**
```
点击右下角「AI 助手」

王销售：「客户说我们的价格太高，我应该如何应对？」

AI 回答：
根据《销售手册》第 3 章和《客户谈判技巧》，建议采用以下策略：

1. **价值强调法**
   突出产品的独特价值和 ROI，而不是直接降价。
   可以计算客户使用我们产品后每年节省的成本。
   
   来源：《销售手册》P23

2. **分期付款方案**
   提供灵活的付款方式，降低客户一次性支付压力。
   例如：首付 30%，剩余 70% 分 12 个月支付。
   
   来源：《客户谈判技巧》P15

3. **案例对比**
   展示同行业客户的成功案例，证明产品价值。
   
   来源：《客户案例库》- 某制造企业案例

建议：优先使用价值强调法，避免直接降价影响利润。
```

**3.3 生成客户跟进邮件**
```
王销售继续对话：
「根据这些建议，帮我生成一份给客户 A 的跟进邮件」

AI：
好的，我已经为您生成了跟进邮件。

[生成 Word 文档]
标题：关于贵司采购需求的跟进.docx

正文：
  尊敬的张总：
  
  感谢您在上周的会议中分享贵司的采购需求...
```

## 七、风险和应对

### 风险 1：组织架构设计复杂度超预期
**影响：** 核心功能延期  
**概率：** 中  
**应对：**
- 简化为单层级结构（MVP 只支持公司 → 部门）
- 延后支持复杂的矩阵式组织
- 使用成熟的树形数据结构库

### 风险 2：AI 扩写质量不稳定
**影响：** 核心卖点效果打折  
**概率：** 高  
**应对：**
- 预先准备 prompt 模板库（销售、研发、财务）
- 建立评估数据集（100 个测试任务）
- 设置人工审核和编辑机制
- 允许用户反馈并迭代优化

### 风险 3：向量数据库部署和维护复杂
**影响：** 知识库功能延期  
**概率：** 中  
**应对：**
- 优先使用云服务（Pinecone）而非自建 Milvus
- 准备降级方案（PostgreSQL 全文检索代替语义检索）
- 延后知识库功能到 P2（如果时间紧张）

### 风险 4：Web UI 开发进度慢
**影响：** Demo 无法完整演示  
**概率：** 中  
**应对：**
- 前期使用 CLI 或 Postman 验证后端功能
- 采用成熟组件库（Ant Design）加速开发
- 降低 UI 美观度要求（功能优先，体验优化放 V1.0）
- 外包前端开发（如果预算允许）

### 风险 5：多租户数据隔离出现安全漏洞
**影响：** 严重安全问题，无法交付  
**概率：** 低  
**应对：**
- 在架构设计阶段充分评审（PostgreSQL RLS）
- 编写自动化测试覆盖所有跨租户场景
- 引入代码审查和渗透测试
- 使用成熟的多租户框架（如果存在）

### 风险 6：团队人力不足
**影响：** 整体延期  
**概率：** 高（如果是 1-2 人团队）  
**应对：**
- 严格控制功能范围（砍 P2 功能）
- 使用更多开源库和云服务（减少自研）
- 调整时间表为保守的 12 周
- 考虑外包部分模块（前端、UI 设计）
